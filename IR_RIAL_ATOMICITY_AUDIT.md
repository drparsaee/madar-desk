# Madar Desk: TOMAN finance / RIAL V2 atomicity audit

Scope: read-only architecture review of `native_app.py`, `app_storage.py`, `lan.py`, `finance.py`, `accounting_service.py`, `money_policy.py`, `ir_journal_v2.py`, and `ir_journal_sqlite.py` as read on 2026-10-22. This report is the only deliverable; no active database, APPDATA, process, network, tests, or release was touched. Line references point to those source files. Findings are source-level, not a runtime/integration test.

## Decision

**Current state: there is NO host API that atomically commits a legacy TOMAN finance update and a RIAL V2 journal update.** The atomicity of `UnifiedAppStorage.commit` covers only its four/five accepted legacy/automation domains. `RIALJournalStorage` uses another SQLite connection and normally a distinct, dedicated SQLite path. The active LAN accounting and finance commands call only the legacy finance commit. A caller that invokes both existing storage methods sequentially can leave only one side committed on a process crash, power loss, CAS rejection, permission failure, or filesystem error.

**Required for strict joint atomicity:** first consolidate both writes into **one local SQLite database, on one connection, under one `BEGIN IMMEDIATE` transaction and one final `COMMIT`**. Put the RIAL V2 journal in an explicitly versioned table/schema inside the authoritative unified database, or in a versioned validated unified bundle with equivalent append-only semantics. Prefer dedicated versioned table(s) in the same database for per-company CAS, independent journal history, and efficient source uniqueness. This requires new APIs: neither storage class currently accepts a caller-owned transaction/connection. Merely passing the same filename to both present classes is unsafe because `UnifiedAppStorage._schema` rejects additional tables, and both classes independently start/finish transactions.

## Security, period, currency, and duplicate-source failure modes

1. **Split commit:** committing finance first and V2 second (or the reverse) exposes a permanently divergent issued document/journal if the later step fails. Different SQLite files/connections cannot be repaired by an in-process mutex or two independent successful CAS checks. `ATTACH` across separate databases is not a safe shortcut to guaranteed crash atomicity with a WAL database; avoid relying on it for this invariant.
2. **Active legacy JSON mode:** `native_app.py:816-818` and `1297-1306` use multiple `atomic_json` writes, which are individually replace-atomic but not a group transaction. Enforce a unified-storage migration gate before enabling **strict dual ledger** operations; older hosts cannot silently downgrade.
3. **Stale fiscal period:** `ir_journal_v2.py:501-547` checks the requested period/date and whether its *in-memory journal state* has a close event; `ir_journal_v2.py:550-583` closes periods. The persisted V2 CAS protects concurrent V2 writers (`ir_journal_sqlite.py:205-242`), but a finance write can currently race with a period close or a changed host accounting configuration. Re-read current company/period policy and journal revision inside the one transaction, serialize both posting and closing through the same host writer, reject posting if closed/stale, and never backdate into a newly closed period. Immutable V2 periods (`ir_journal_sqlite.py:73-78`) need an explicit, versioned period-calendar change workflow rather than unsanctioned edits.
4. **Authorization boundary:** LAN authenticates bearer sessions (`lan.py:287-296`) and old reducers check privileges (`finance.py:143-183`; `accounting_service.py:164-167`). V2 `VerifiedScopes` expressly requires trusted host-derived memberships (`ir_journal_v2.py:108-141`); journal source IDs alone are not ownership proof (`ir_journal_v2.py:77-104`). A new posting endpoint must derive actor, company, project, task/checklist, party, and document scopes from authoritative host data and recheck rights under the same serialization guard. Never trust a client-supplied `actor_id`, chart evidence, `VerifiedScopes`, company ID, fiscal-period selection, or unit conversion assertion.
5. **Cross-ledger duplicate:** legacy accounting links already reject reuse of some task and purchase-cost sources (`accounting_service.py:275-313`); V2's unique key blocks duplicate **V2** source records (`ir_journal_sqlite.py:56-70`). Neither prevents the same invoice/cost being counted once in old GL and again in V2. Define a host-owned canonical commercial-source key (company, business-document type, document ID and posting purpose; also project/task/cost IDs as verifiable provenance), make mapping from old document/event to V2 journal unique in the authoritative SQLite transaction, and atomically store the mapping with both updates. Reject a second mapping with a different event ID; return the original result for exact retries; require explicit approved reversal/correction workflows.
6. **Currency drift/rounding:** legacy read model emits TOMAN (`accounting_service.py:408`) while V2 requires exact integer RIAL (`money_policy.py:13-17`, `ir_journal_v2.py:516-520`). Gate migration on verified TOMAN provenance/digest and exact x10 conversions. For posted documents, freeze original source totals, conversion evidence, and company policy; reject float, silent rounding and integer overflow. The conversion helper is a *preview* (`money_policy.py:284-322`), not an authorized host migration.
7. **Rollback/restore:** legacy unified restore appends old revisions (`app_storage.py:373-396`); V2 history is append-only (`ir_journal_sqlite.py:73-83`). Restoring a previous legacy balance without a corresponding reviewed V2 adjustment makes ledgers diverge. Block finance-altering historical restore while V2 mode is active, or implement an auditable compensating transaction preserving issued documents and event history. Backups must cover the entire single authoritative DB and schema version.
8. **Server lifecycle/operations:** two independent SQLite stores may use different busy timeout, WAL/synchronous settings (`app_storage.py:245-250`; `ir_journal_sqlite.py:151-158`), with distinct crash and backup semantics. One authoritative writer/connection removes the cross-file consistency problem; connection-local checks must be enforced on every transaction.

## Safe phased implementation and gates

**G0: inspect and freeze the contract (no production writes).** Record authoritative host mode (legacy JSON vs unified SQLite), verified company/actor/project mappings, source documents, fiscal calendars, and currently supported accounting commands. Define which ledger is authoritative at each phase and whether an operation causes exactly one commercial posting. Confirm all old-data amounts really are TOMAN with source evidence. Prepare a backup/restore drill on synthetic copies; block switch-on without a validated baseline. Keep raw customer data and APPDATA untouched during development.

**G1: schema migration on an isolated candidate.** Introduce `SCHEMA_VERSION=2` plus a specifically reviewed marker upgrade, preserving schema-v1 readability/backup. Create V2 journal and immutable bridge/source-index tables in the *same* `madar-unified.sqlite3` via a versioned, fail-closed SQL migration. Decide explicit treatment for a host still in JSON mode: require opt-in legacy-to-unified migration before V2 dual writes. Existing `UnifiedAppStorage._schema` exact table set and bridge's fixed marker (`app_storage.py:255-282`, `native_app.py:425-434`) require coordinated changes. Rehearse power-loss/corrupt-migration rollback with *synthetic* databases.

**G2: one host-owned transaction.** Provide a connection-bound primitive, e.g. `commit_finance_and_rial(candidate_finance, journal_operation, expected_app_revision, expected_rial_revision, verified_context)` that obtains a single SQLite connection, `BEGIN IMMEDIATE`, reads **both** current heads and company-period/unique-source constraints, revalidates scoped chart/party/task + authorization + conversion evidence, reduces and validates both candidate states, inserts the legacy revision and RIAL append/source mapping, then `COMMIT`s once; on any exception `ROLLBACK`s both. Refactor storage internals so they do not each open/commit their own connection when called by the host transaction. Source-index uniqueness must be a SQL constraint or an equally serialized persistent invariant, not a client event ID check. No partially successful return or issue-number publication before the transaction commits.

**G3: host command and LAN adapter.** Route issuing/posting sales invoices, purchase bills and appropriate expense/task transitions through the new host-only primitive. Obtain the actor from `LanService.account_for`, consult current server roles and project grants, derive `VerifiedScopes`, company and fiscal period from trusted server state. Client sends intent with a stable business source/idempotency key; server derives final posting and document; repeated exact intent returns same receipt; changed payload for same event/source conflicts. Restrict period close, reversal, source remap, and historical restore to explicit admin-authorized operations; keep existing read endpoints behavior until reconciled.

**G4: shadow reconciliation and activation.** On synthetic copies first, import verified TOMAN history to a RIAL comparison view using x10, compare per-company/per-period/source: issued documents, payable/receivable, debit-credit, reversals, closed periods, rounding, and unmatched records. Shadow projections must never create a second revenue/cost posting. Enable operational dual writes only after zero unexplained source divergence, no unauthorized cross-project visibility, and adequate backup/restore evidence. During migration, freeze or carefully sequence legacy-only writes; otherwise catch-up results become stale immediately.

**G5: targeted adversarial validation before release.** Test synthetic failures immediately before SQL `COMMIT`; stale app revision; stale journal revision; concurrent issuance with different event IDs for the same commercial source; concurrent period-close/post; LAN editor without `financeEdit`; wrong company/project; forged `VerifiedScopes`; payment/issue retry; reversal followed by attempted duplicate repost; overflow and fractional-TOMAN boundary; restore downgrade; WAL recovery; backup and restore. For every injected failure assert either **both** TOMAN and RIAL states advance or **neither** does. Only then test a candidate native EXE and LAN flow with fully isolated scratch data, and require explicit production deployment review.

## Integration acceptance condition

Strict atomic migration is ready only if **one SQLite commit** contains the legacy finance update, the V2 journal append, and the canonical source mapping, with both revision checks, host authorization, company isolation, current period validation, and complete rollback verified under synthetic concurrency/failure tests. In the present code none of those cross-ledger atomicity conditions is implemented. This audit changes no execution path and does not claim PASS for security, integration, or runtime tests.

## Follow-on: embedded finance-domain RIAL V2 candidate (2026-10-22)

This follow-on source change introduces `ir_finance_v2_extension.py` and modifies **only** the optional finance validator in `finance.py`. It changes the earlier audit's possible migration approach: V2 can be embedded as **data inside the existing finance JSON domain**, allowing the existing `UnifiedAppStorage.commit` to commit legacy TOMAN and RIAL V2 under the **same finance revision CAS**. The earlier discussion of required schema v2/table upgrades applies to a future separate-table solution; embedded V2 does *not* require SQLite schema/table modifications. This is an architectural capability only: no caller in `native_app.py` or `lan.py` has been changed by this worker and no runtime atomic posting is asserted.

### Serialized contract and pure APIs

`finance["rialJournalV2"]` is an **opt-in** map with exactly `{"schemaVersion": 1, "companies": {company_id: {"revision": sha256_revision, "snapshot": canonical_json_rial_state}}}`. The nested snapshot is the canonical JSON representation of `ir_journal_v2.JournalState` (periods, chart/scope evidence, hash-chained events, currency `RIAL`). `finance.validate_finance_state` accepts the extra field only when fully replayable and schema-valid via `validate_rial_finance_extension`; pre-existing snapshots without that field remain supported, and `empty_finance_state` still emits no V2 field.

`activate_rial_finance(finance_state, pristine_journal, *, proof=HostCompanyProof(...))` returns a detached finance state with an empty company journal. `load_finance_rial_journal(finance_state, company_id)` reads and validates one company. `compose_finance_rial_snapshot(finance_before, finance_after, candidate_journal, *, expected_journal_revision, proof=VerifiedInvoiceSourceProof(...))` returns one combined finance snapshot suitable for **one** storage CAS commit. It accepts precisely one freshly issued legacy TOMAN sales invoice and one new RIAL V2 task/card journal event. The composer checks original ledger/invoice/contract history, legacy receipt invariants, event actor/project/card/issued invoice provenance, journal revision, immutable V2 periods/chart/evidence/events, and exact gross TOMAN x10 = RIAL debit. It refuses unrelated changes to the independent historical accounting domains. Both serializers and reducers are pure; only the external host decides when/how to store the result.

The `HostCompanyProof` and `VerifiedInvoiceSourceProof` immutable dataclasses are **host-side evidence carriers, not cryptographically authenticated identities**. Their digest bindings detect stale/mismatched detached snapshots, but a caller could fabricate an object. The host must authenticate the user and company, confirm current party/task/job and project grants, derive V2 `VerifiedScopes` and policy from authoritative state, and ensure the newly issued finance result was produced by an authorized reducer. No HTTP/UI endpoint may trust proof objects coming directly from clients. Old TOMAN numbers are never rewritten or silently reinterpreted; RIAL amounts must be expressly generated and checked. The current narrow composer **does not** support purchases, invoices in the independent accounting extension, reversal, period close, batch posting, or historical migration. Those require explicit reviewed adapters and source-index reconciliation.

### Validation and remaining gates

Source tests in `tests/test_ir_finance_v2_extension.py` exercise opt-in compatibility and JSON serialization, strict per-company schema and revisions, single-issued-invoice composition, attempted tampering of evidence/snapshots, rejection of historical TOMAN mutation and duplicate business sources, and invalid currency/amount mismatch. Following the in-process code changes, **72 tests passed** using `python -m unittest tests.test_ir_finance_v2_extension tests.test_finance tests.test_accounting_service tests.test_ir_journal_v2 -q` (run from the Madar Desk folder). The initial broader command that also included `tests.test_app_storage` could not import its sibling `test_data_model` because of module invocation layout; no app-storage test PASS is claimed from that attempt. A pure `app_storage.validated_bundle` check *was* exercised in the new tests; no SQLite/database test was run by this worker.

**Before enabling any host posting**, Prime must read/reduce/compose and commit **one complete finance bundle in one authoritative `UnifiedAppStorage.commit(expected_revision=...)`**, deriving source proof under the host lock and checking current V2 revision in the candidate. The finance field must be retained during every ordinary TOMAN/accounting command and included in backups. Run isolated host rollback, concurrent issue/close/reversal, stale app-CAS/V2-CAS, older-client preservation, LAN authorization, schema-size and restoration tests. Legacy JSON mode cannot give strict crash-atomic multi-domain guarantees; keep dual-ledger posting gated to unified SQLite and fail closed for unsupported modes. This phase had no persistence changes and no production/runtime security PASS claim.
