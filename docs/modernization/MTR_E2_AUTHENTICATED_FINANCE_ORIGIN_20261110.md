## Host-only interface

The trusted host must instantiate exactly one `HostAuthenticatedFinanceOrigin` for its current `LanService`, with an **operator-provisioned** organization/sender/key, 32-byte-or-longer private Madar-direction HMAC key, and a trusted selected 32-hex Taraz company ID. It must not mount this object as a client-constructible RPC endpoint.

1. `prepare_manual(token, source_raw, invoice_id=..., issue_event_id=..., explicit_manual_action=True)` authenticates the **current real `LanService.account_for(token)`** under the host/bridge locks. It demands the *identical dictionary object* from `service.users` and derives `actorId` from the private `accountLineage`. It rejects missing/duplicated lineage, viewer role, editor without `financeEdit=True`, revoked session, inactive account, missing project grants or deleted task. It rederives the project/title/expense amount from the saved card via `taraz_exchange._build_proposal`. The supplied canonical source bytes must match that saved task exactly, with a positive selected RIAL expense. It then issues a domain-separated, HMAC-SHA256 **process-only** one-use `SealedFinanceOrigin` over immutable actor/org/current session hash/role/grants/task digest, original request ID/source SHA-256, company/invoice/issue/journal identifiers.
2. `sign_original_manual(token, seal, source_raw, explicit_manual_action=True)` verifies and consumes the sealed 30-second capability; it independently reloads current private account, role, session, project grants and saved task, then calls the existing `mtr_peer_envelope.sign_request`. The v2 original has purpose `finance_review_request`, actor role taken **only** from the authenticated host, and exact body keys `id,taskId,projectId,sourceDigest,companyId,actorId,invoiceId,issueEventId,journalId`. The invoice IDs must be supplied by the trusted operator integration, not by arbitrary client JSON. No network calls or financial commands execute.
3. `sign_query_manual(token, original_wire, source_raw, query_request_id=<fresh 32hex>, explicit_manual_action=True)` verifies the original HMAC, exact issued wire digest and original local signer ownership, then rechecks the live host actor/project/task/source under lock. It signs one v2 `receipt_lookup` query per original, and refuses reuse of either original or query nonce within the same live signer.

Tests invoke **the real `LanService.account_for(token)`** against an in-memory synthetic registry and actual session table, then independently pass the v2 original/query to the **current Taraz `taraz_mtr_peer_registry._verify`** imported read-only from its isolated worktree. Coverage includes spoofed actor role even when caller can construct an arbitrary HMAC envelope, different login/user, revoked session, role/finance/project changes, changed saved expense, different source bytes/amount, duplicate or missing account lineage, malicious seal mutation, missing manual consent, replay, parallel claims, short expiry and cross-organization rejection. Data is scoped to `TemporaryDirectory` and an in-memory bridge. No LAN server starts.

## Precise blockers before full Madar ↔ Taraz finance binding

- **Identity representation conflict, confirmed in current source:** Madar `mtr_account_lineage.principal_actor_id` yields `mtr-actor-v1-` followed by 64 hex digits, **77 characters**. Taraz `standalone_accounting_identity._USER` restricts its authenticated local username to **3–40 characters**. The existing `taraz_mtr_finance_binding_authority` requires original `payload.actorId == authenticated Taraz username`. A legitimate host-private Madar lineage identity **cannot pass** this equality check. Do **not** substitute a username or truncate/hash a mapped value in Madar: that would lose the immutable identity contract. Taraz needs its own read-only independently authenticated mapping from **external Madar lineage actor ID** to a separately authenticated Taraz operator (or an explicitly approved company/org trust policy), with provenance, authorization, revocation, audit and anti-replay. The Taraz financial operator still needs its native company/session/finance ACL. No such mapping was installed by this worker.
- **Durable transport and replay:** The new source only keeps signatures, sealed nonce consumption and one query challenge in process memory. A restart invalidates its private seals but clears the used original/query sets. Production signing must use the existing host's **durable original request/dispatch replay authority**, current authz epoch and authoritative source bytes, and must record the challenge/consumption atomically under that host authority before any external send. These existing entry points cannot be wired under the worker's NEW-files-only ownership. Creating a new signer in the same host would also get a distinct in-memory replay map; the trusted host composition root must prevent this and own durable one-time state.
- **Source provenance:** The current `MtrLanFinanceAdapter.prepare` produces only task/title/project metadata and does not require a selected positive RIAL expense. The existing `taraz_exchange._build_proposal` supports authoritative selected `expenseId/amountRial`, which the new helper requires. Production must tie this source to the **same durable, originally authorized** request as `HostRequestStore`; accepting arbitrary newly supplied file bytes is insufficient without that durable ownership check.
- **Peer identity and financial receipt:** v2 HMAC verifies the configured direction key, not a live user identity at Taraz. Taraz's reviewed metadata acknowledgement explicitly creates no financial events. The Taraz-side existing booking check currently reads an actual preexisting journal, but `invoice.create.sourceType/sourceId` remain caller-controlled. A separate trusted finance issuer/verifier remains required for **official signed accounting receipts**. A signed Madar original or metadata review cannot promote an existing ledger row into official finance success.
